# Optional cloud architecture

The app is now branded Settler. Its cloud Auth callback remains `pocketbook://cloud/callback` to preserve existing Supabase redirect configuration. Both `settler` and `pocketbook` URL schemes are registered in the native app.

Receipt attachments are device-local in MVP v2: their files and metadata are excluded from cloud backups and sync. Share copies separately before changing devices.

Cloud is opt-in. Ordinary local transactions, exports and recovery remain free and offline. The backend defaults cloud backup and sync to free access; a trusted server policy can later require RevenueCat entitlements. No client premium flag grants backend access. No project has been provisioned in this session; migrations/functions must be deployed before using cloud screens.

SQLite schema 4 adds stable UUID mappings, an atomic outbox, remote revision cache and owner binding. Local integer financial IDs are retained. SQL mutation triggers collect dirty rows; a database adapter captures complete changes before the same transaction commits. Canonical remote rows replace local numeric foreign keys with global UUIDs. Each outbox operation has its own idempotency UUID and expected server record revisions. Failed network attempts retain the exact operation for retry.

Postgres stores versioned canonical records, owner-scoped operation receipts and conflict proposals. Each owner has a serialized authoritative revision head. Writes only occur through a checked RPC; all related references belong to the same owner, posted journals/lines are immutable, journals balance, and active transaction projections match their journal lines. Server update times and revisions determine concurrency, not device wall clocks. Hard deletion is represented by retained tombstones; old devices cannot recreate an existing UUID with revision zero.

Devices upload pending operations before pulling. Independent new transactions merge. Concurrent edits or duplicate recurring business keys create a persisted conflict with both proposals; the entire affected financial batch remains unapplied. Sync stops on conflict. The review workflow can retain a local recovery/proposal backup and explicitly adopt cloud data, or leave the conflict pending and review/re-enter a corrected financial event using the ordinary reversal editor. No automatic last-write-wins financial overwrite is performed. Incoming batches materialize atomically from the validated remote cache only after pending writes are acknowledged.

Initial adoption validates local integrity and explains the upload. An empty cloud dataset accepts the initial records idempotently. A nonempty cloud dataset requires an explicit cloud restore with a local recovery copy; automatic merging of two unrelated legacy datasets is intentionally unsupported. Sign-out stops cloud work without deleting local data. Owner binding prevents another account from inheriting a previous owner's pending records. Cloud deletion removes owned remote records and Storage objects through a trusted server function; local data remains available, detached from cloud.

Backups are complete versioned JSON snapshots with digests, private Storage paths and owner-controlled manifests. Upload success requires server verification against downloaded bytes. Backup creation has a server-enforced count cap (5, or 30 with extended history); deletion is explicit, never silent. Failed uploads retain a pending manifest that can be deleted/retried. Plain cloud data is readable by the backend operator and protected by TLS, RLS and the project's configured storage-at-rest controls. This is not end-to-end encryption; client password-encrypted backups are a separate local-export feature. Users see privacy information before enabling cloud.

When subscription access ends, local data and export remain available; owned cloud snapshots and records remain readable for recovery, but premium-required writes stop. RevenueCat SDK purchases/restores are refreshed through a trusted server API using the authenticated UUID as app user ID. Webhooks trigger a server-side provider re-fetch, not a blind event boolean. Cancellation alone does not revoke an unexpired entitlement. No billing provider configuration means no purchase flow or premium claims.

## Provisioning and deployment

No Supabase project or billing credentials were provided. All cloud features remain unconfigured until the following deployment is performed. Local finance continues to work without environment variables.

1. Create a dedicated Supabase project, install the Supabase CLI and authenticate. Link it using `supabase link --project-ref YOUR_PROJECT_REF` and review pending migrations with `supabase db push --dry-run`. Apply the four checked-in migrations using `supabase db push`. Never run a reset against a production project. These steps follow the [official migration workflow](https://supabase.com/docs/guides/deployment/database-migrations).
2. Deploy `backup-manager`, `account-delete` and `entitlements` using `supabase functions deploy FUNCTION_NAME`. Deploy `revenuecat-webhook` only when billing is configured. Its JWT gateway check is intentionally disabled in config; its own secret authorization check is required. Server functions use platform-provided Supabase server credentials. Privileged keys must never be included in Expo public variables.
3. Copy `.env.example` to an ignored local `.env`. Set only the project URL and public publishable/anon key for Supabase. Build-time checks reject recognizable service-role/secret keys. Rebuild the native app after environment or native billing configuration changes.
4. Enable email/password Auth, production email delivery, rate limits and email confirmation. Add `pocketbook://cloud/callback` to permitted Auth redirects. Test signup, confirmation, PKCE password reset, expired sessions and sign-out on real devices. OAuth is not enabled by this implementation.
5. The trusted `cloud_policy` defaults `free_cloud=true`, as requested. Leave RevenueCat public and server keys blank for free cloud. For a later paid policy, configure store products, packages and matching entitlement IDs (`cloud_backup`, `multi_device_sync`, `extended_backup_history`, `advanced_reports`). Put `REVENUECAT_SECRET_API_KEY` and `REVENUECAT_WEBHOOK_AUTH` only in Edge Function secrets. Configure the webhook authorization header to that secret and its endpoint to `/functions/v1/revenuecat-webhook`. The SDK user ID is the authenticated UUID. Use store sandbox purchases/restores before changing the trusted policy.
6. Inspect deployed RLS and private bucket policies, function logs without tokens or financial payloads, project backup/retention controls and operational alerts. Test owner isolation using two accounts and independent devices before a production rollout.

Foreground network/resume events and local mutation signals retry sync. A 30-second foreground poll also catches settings or schedule mutations; no guaranteed background execution is promised. Sync caps a dataset at 10,000 canonical records, including accounting history, and a batch at 20 MB. Backups have a 20 MB limit and explicit count caps; pending uploads count toward retention. Large datasets require backup recovery rather than pretending synchronization succeeded. Conflict adoption preserves a local recovery file; keeping an alternative edit requires review/re-entry through the accounting editor, not an automatic override button.

Session ciphertext lives in AsyncStorage using AES-GCM; only its 32-byte key is stored in SecureStore. Cloud data is not end-to-end encrypted. SQLite remains the local financial store with the security limits described in SECURITY.md. Offline account deletion cannot be completed remotely; the local dataset is retained.

Automated tests run these migrations against PostgreSQL via PGlite with mocked Auth/Storage schemas and exercise real SQLite outboxes. They cover atomicity, idempotency, independent device merge, conflict retention, RLS ownership, forged references, entitlement write denial, expired-access recovery, encrypted session storage and public-key guards. These tests are not a deployed Supabase Auth/Storage/Edge Function or billing integration test. Deno and a provisioned project are unavailable here; deployment and native integration remain to be verified.

## Play release gate

The local release profile in `src/release/profile.json` explicitly disables online accounts and purchases. Adding environment keys does not enable them; `app.config.js` rejects feature/profile drift. Android autolinking excludes the native RevenueCat SDK. The provisioning instructions above apply only to a future audited cloud release that revises these controls and rebuilds the native app. Settings hides the inactive cloud entry, and billing does not initialize an anonymous customer on startup. Re-audit before enabling either service: deploy and test deletion (including service-provider data), provide the external deletion request link, revise the app-specific privacy notice and Data safety, and replace the existing price-only purchase dialog with complete, verified plan/introductory-offer terms. A store subscription management link is now present; it does not make the dormant paywall release-ready. See [PLAY_POLICY_AUDIT.md](PLAY_POLICY_AUDIT.md).

Public minimum-version checks use a separate anonymous Supabase client with no persisted login or token refresh. Configuring the public update backend does not enable sign-up, cloud uploads or purchases. `npm run play:guard` verifies the local feature profile and billing exclusion; it does not approve Play Console declarations or release publication.
